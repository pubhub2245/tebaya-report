# Phase 1 UI 設計案

> ⚠️ **本書は提案ドキュメント**。実装はしない。

## 全体方針

シフトに 3 状態（confirmed / pending / rejected）を持たせ、**色＋アイコン＋（rejected の取り消し線）**で視認性を確保する。
既存の `/shifts`（公開カレンダー）と `/admin/shifts`（編集カレンダー）両方で統一感を出す。

## 3 状態の表示規約

| 状態 | 絵文字 | 背景色 | 文字色 | 装飾 | 説明 |
|---|---|---|---|---|---|
| 🟢 confirmed | ✅ | `bg-green-50` 〜 `bg-green-100` | `text-green-900` | なし | PDF で確定済み（手羽屋記載） |
| 🟡 pending | ⚠️ | `bg-yellow-50` | `text-yellow-900` | `border-yellow-300` | 希望メール送信済み・PDF 未反映 |
| 🔴 rejected | ❌ | `bg-red-50` | `text-red-700` | `line-through opacity-60` | 大田原さんから却下された |

### Tailwind クラス具体案

```tsx
// 共通バッジ用
const STATUS_CHIP: Record<ShiftStatus, string> = {
  confirmed: "bg-green-50 text-green-900 border-green-300",
  pending:   "bg-yellow-50 text-yellow-900 border-yellow-300",
  rejected:  "bg-red-50 text-red-700 border-red-300 line-through opacity-60",
};

const STATUS_ICON: Record<ShiftStatus, string> = {
  confirmed: "✅",
  pending:   "⚠️",
  rejected:  "❌",
};

const STATUS_LABEL: Record<ShiftStatus, string> = {
  confirmed: "確定",
  pending:   "希望中",
  rejected:  "NG",
};
```

### rejected の「取り消し線で残す」具体例

```tsx
<div
  className={`rounded-lg p-2 ${STATUS_CHIP[status]} ${
    status === "rejected" ? "line-through opacity-60" : ""
  }`}
>
  {STATUS_ICON[status]} {storeName}
</div>
```

`line-through` で打消し線、`opacity-60` で薄く見せる。
**消さずに残す**理由: 大田原さんとの履歴を可視化、再申請・代替検討時の参照に使える。
オプションで「NGも表示」トグルを置き、デフォルトは表示にする。

│  ┌──────────────────────┐ │

│  └──────────────────────┘ │

└───────────────────────────┘

各エントリは小さな chip にして、上から **confirmed → pending → rejected** の順に並べる
（重要なものを上に）。

#### プレビュー画面の主要コンポーネント

1. **本文入力エリア**（textarea, monospace, 20行）
2. **「解析する」ボタン** → クライアント側で `parseRequestEmail` を呼ぶ（API ルート不要）
3. **警告表示エリア**
   - warnings 配列を箇条書き
   - 黄色背景 `bg-yellow-50`、左ボーダー `border-l-4 border-yellow-400`
4. **月別サマリーテーブル**
   - 月ごとに店舗 × 希望日のグリッド
   - クリックで日付の詳細ポップオーバー（必要なら）
5. **重複チェックセクション**
   - 既存 shifts と (date, location) でぶつかる希望日
   - 個別に「スキップ／上書き」を選べる UI
6. **コミットボタン**
   - **確認モーダル** を出す（「○月○日分 X 件を pending として登録します。よろしいですか？」）
   - OK で `/api/shift-import` POST → DB INSERT

#### 失敗時の挙動

- 解析エラー（例: ヘッダーなし）→ プレビュー領域に「ヘッダーが見つかりません」表示、コミットボタン disabled
- DB INSERT 失敗（重複等）→ アラート＋未確定なので何度でもやり直せる旨を明記

### 5. 既存「未確定バッジ」UI の流用

PR #5 で実装済みの未確定バッジ UI（`【未確定】`/`【スタッフ要設定】`の黄/橙背景）は
Phase 1 でもそのまま活用できる：
- `note LIKE '%【未確定】%'` 判定 →  `shift_status === 'pending'` に置き換え
- バッジの色・絵文字・配置は流用

→ **PR #5 のバッジ部分（`44fdde2`）は新ブランチに cherry-pick または再実装**で持ち込む。

## 設計上の判断ポイント（じゅんさん確認推奨）

1. **rejected の表示**: 「取り消し線で残す」は仕様書通り。デフォルト ON で OK か？
2. **凡例の位置**: カレンダー上部 vs 凡例ヘルプボタン。スマホ画面の専有面積考慮。
3. **メール本文貼付方式 vs Gmail 直接連携**: Phase 1 は手動コピペ前提でいいか？
   将来的に Google API 連携で自動取得もあり得るが、認可手続きが面倒。
4. **重複検出の単位**: `(date, location_id)` で十分か？ あるいは `staff_name` も含めるか？
   → 推奨: `(date, location_id)` のみで判定（同日同店舗は 1 件まで運用）。
5. **「上書き」した場合の旧レコード**: 物理削除 vs 履歴保持？
   履歴保持なら `audit_log` テーブル別途必要（Phase 1 では時期尚早かも）。
6. **モバイル対応**: シフト管理は外出先でも見る運用。
   カレンダーの 1 セル小さい問題対策として「リストビュー優先」モードを用意するかも。
