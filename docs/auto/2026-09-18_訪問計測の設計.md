# サイトに来た人を数える仕組み（設計）

2026-09-18 じゅんの答え **c8**「『サイトに来た人の数（週）』を次の目標にする。数える仕組みは
Claudeが無料の方法で作る」を受けた設計です。司令室のタスク **c6**（SNSのクリック計測）も
同じ仕組みで一緒に片づきます。

## 1. 何のために作るか

ここまでは「作ったページの本数」を先行指標にしてきました。ページを作る側はだいたい
やり切ったので、次は **来た人の数** を見たい。ところが、いまはどのサイトにも
訪問を数える仕組みがありません。

## 2. なぜ外部のサービスを使わないのか

| 案 | 費用 | じゅんの作業 | 司令室が読めるか | 判断 |
|---|---|---|---|---|
| Vercel Analytics | 無料枠に上限あり（超えると課金の芽） | なし | 読めない（画面だけ） | 見送り |
| Google Analytics | 無料 | アカウント作成・タグ設定 | 読むのに鍵が要る | 見送り |
| Cloudflare / Umami など | 無料枠あり | アカウント作成（5サイト分） | 鍵が要る | 見送り |
| **すでにある倉庫（Supabase）に自前で1行足す** | **0円** | **表を1回作るだけ** | **まとめ用のURLを読むだけ** | **採用** |

固定費ゼロ・じゅんの作業は1回きり・司令室が自動で読める、の3つを満たすのは最後の案だけでした。

## 3. かたち

```
  5つのサイト                   ここ（tebaya-report）              倉庫
 ┌──────────────┐   合図   ┌──────────────────┐        ┌──────────────┐
 │ Play Miyazaki │ ───────▶ │ POST /api/hit     │ ─────▶ │ site_visits  │
 │ AIツールナビ   │          │（数える受け口）    │        │（1行＝1訪問）│
 │ 煙道 ENDO     │          └──────────────────┘        └──────────────┘
 │ ビルドナビ     │                                             │
 │ 経理パッケージ │          ┌──────────────────┐               │
 └──────────────┘          │ GET /api/hit/summary│ ◀────────────┘
                             │（週ごとの合計だけ） │
        司令室（毎時） ──────▶└──────────────────┘
```

**鍵を1か所にまとめるのが肝**です。5サイトそれぞれに倉庫の鍵を配ると、鍵が5か所に増え、
2026-08-28 のような「鍵の値が壊れて全部止まる」事故の面が広がります。鍵を持つのはこの
アプリだけにして、ほかの4サイトからは「開かれました」という合図だけを送ってもらいます。

## 4. 集めるもの・集めないもの

| 集める | 集めない |
|---|---|
| サイト名（5つのどれか） | IPアドレス |
| 開かれたページの場所（`?` より後ろは捨てる） | ブラウザの種類（UA） |
| 合言葉 `utm_campaign`（SNS投稿の効き目を見る） | お客さんを見分ける印・cookie |
| 来た元のドメイン名だけ（例 `t.co`） | 細かい元URL |
| 開かれた時刻 | 名前・メール・その他の個人情報 |

ブラウザの種類（UA）は「ロボットかどうか」を見るためだけに使い、**保存しません**。
検索エンジンの巡回を「人が来た」と数えると目安になりません。

## 5. 壊れない作りにしてあること

- 受け口は**どんなときも 204（成功）**で終わります。倉庫が落ちていても、合図を送った
  サイトの表示は1ミリも変わりません。
- 合図はページの表示が終わってから送ります（表示を遅らせない）。
- 許した住所（5サイト）以外からの合図は数えません。
- 表の鍵（RLS）はポリシー無し＝**サーバーの鍵からしか触れません**。ブラウザから
  直接読み書きはできません（`table_snapshots` と同じ考え方）。
- 手羽屋の日報・シフト・レジ・LINE・お金の計算には一切触れていません。表も別です。

## 6. 数えないページ

経理の画面（`/keiri`）・初回設定（`/keiri/welcome`）・立替の入力（`/keiri/advances`）と、
手羽屋の業務画面は**数えません**。お店の人が仕事で開く画面なので、「サイトに来た人」に
混ぜると目安が狂います。数えるのは外向きの10ページだけです。

## 7. 司令室がどう読むか

`GET /api/hit/summary` が、こういう形で合計だけを返します（1行ずつの記録は外に出しません）。

```json
{
  "ok": true,
  "generatedAt": "2026-09-18T07:40:00.000Z",
  "last7days": { "playmiyazaki": 0, "keiri": 0 },
  "weeks": [{ "weekStart": "2026-09-14", "sites": { "playmiyazaki": 0 } }]
}
```

司令室は毎時これを読んで、各案件の「サイトに来た人の数（週）」を更新します。

## 8. 進め方（この下書きの範囲と、次）

**この下書きに入っているもの**

1. 表を作るSQL（`supabase/migrations/site_visits.sql`）
2. 数える受け口（`app/api/hit/route.ts`）とまとめ窓口（`app/api/hit/summary/route.ts`）
3. 計算だけのファイル（`lib/siteVisits.ts`）と検算10件（`tests/siteVisits.test.ts`）
4. 合図を送る小さな部品（`components/VisitBeacon.tsx`）と、経理パッケージの10ページへの取り付け

**じゅんの作業（1回だけ）**

- Supabase の SQL Editor で `supabase/migrations/site_visits.sql` を貼って実行する。
  （何度実行しても安全。既存の表には触れません）

**次の回（この下書きが本番に入ってから）**

- 残り4サイト（Play Miyazaki・AIツールナビ・煙道ENDO・ビルドナビ）に、同じ部品を
  3行ずつ入れる。環境変数の追加は**不要**です（合図の送り先が決まっているため）。
- 各案件の先行指標を「サイトに来た人の数（週）」に置き直す。

## 9. ほかのサイトへの付け方（次の回の control 用）

各サイトのいちばん外側のレイアウトに、この3行を足すだけです。

```tsx
import VisitBeacon from "@/components/VisitBeacon"; // 同じ中身のファイルを置く
// ...
<VisitBeacon site="playmiyazaki" />
```

`site` に入れる名前は `playmiyazaki` / `ai-tools-navi` / `endo` / `mh-build-roadmap` / `keiri`
の5つだけです（`lib/siteVisits.ts` の `KNOWN_SITES`）。
