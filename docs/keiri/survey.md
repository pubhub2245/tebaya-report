## 2. 「売上」はどこに入っているか

### 2-1. 本体：`daily_reports`（粒度＝**1日 × 1出店場所**）

| カラム | 型 | 中身 |
|---|---|---|
| `date` | date | 営業日 |
| `shop` | text | お店区分（手羽屋 / もも屋） |
| `location` | text | 出店場所（文字列。`locations` とはIDで繋がっていない） |
| `staff_name` | text | 担当者（共同出店は「A、B」のように1セルに複数名） |
| `sales_amount` | integer | **その日の売上合計（税込・円）** |
| `cumulative_sales` | integer | 累計売上（表示用） |
| `product_counts` | jsonb | 商品ごとの販売本数 `{商品名: 本数}` |
| `product_prices` | jsonb | その日に使った単価 `{商品名: 単価}`（値上げしても過去が壊れない控え） |
| `breakdown_total` | integer | 「単価×本数」の合計 |
| `breakdown_diff` | integer | `売上 − 内訳合計`。0なら一致 |
| `breakdown_diff_reason` / `_note` | text | 合わなかった理由 |
| `alcohol_count` / `allstar_count` / `customer_groups` | integer | お酒本数・オールスター本数・客組数 |

→ **売上は「日次の合計金額」だけで、取引1件ごと（レシート1枚ごと）ではない。**
　 会計上は日次合計で仕訳を起こす（＝1日1行の売上仕訳）方式になる。

→ **売上は現時点で全額が現金**（2026-08-25 川畑さんに確認）。
　 PayPay等のキャッシュレス決済は使っていないため、現金とキャッシュレスを分ける必要はない。

### 2-2. レジまわり

| カラム | 中身 |
|---|---|
| `register_coins` (jsonb) / `register_total` | 閉店時のレジ金の内訳と合計 |
| `register_ok` (bool) / `register_diff` (int) | レジが合ったか／過不足額（マイナス＝不足） |

`setup_checks` にも開店前の `register_total` / `cash_diff` があり、前回との差を見ている。

## 3. 「経費」はどこに入っているか

### 3-1. 本体：`daily_reports.expenses`（jsonb 配列）

1行の形：
```json
{ "description": "場代", "amount": 3000, "receipt_image_url": "data:image/jpeg;base64,..." }
```

- 入力場所：`/report` の STEP5「立替経費」（`app/report/page.tsx`）
- レシート写真からOCRで金額を自動入力できる（`/api/ocr`）
- `expenses_total` というカラムも存在するが**バグのため使われていない**。
  金額の集計は毎回 jsonb 配列を足し直している（`app/cash/page.tsx` の `sumExpenses`）

**実データに入っている `description` の上位（実DB集計）**

| 内容 | 件数 | 経理的にはたぶん |
|---|---|---|
| 場代 | 90 | 出店料 → 賃借料 |
| 肉代／手羽代 | 38 | 仕入・鶏肉 |
| ポテト／ポテト×2 | 29 | 仕入 |
| レジ袋／袋／内レジ袋 | 34 | 消耗品費 |
| ミンチ／キャベツ／ニラ／片栗粉／油／料理酒 | 各数件 | 仕入（餃子材料・粉/油/調味料） |
| ペーパー／ラップ／ガムテープ／ゴム手袋／おしぼり | 各数件 | 消耗品費 |
| 一ツ葉有料道路 | 3 | 旅費交通費（高速代） |
| コピー代／ラミネート／伝票 | 各数件 | 事務用品費？（要判断） |
| さとみさん研修 | 3 | ？（要判断） |

→ **経費は「自由入力の文字」しかなく、勘定科目の分類が付いていない。** ここが変換層の最大の課題。

### 3-2. 使われていない `expenses` テーブル

`supabase/schema.sql` に `expenses`（report_id で `daily_reports` に紐づく）が定義されているが、
実DBには存在せず、コードからも参照されていない。**経費は jsonb 側が実態。**

### 3-3. 人件費（給与）

- `daily_reports.labor` … その日その人に払う日当（円）。共同出店は人数で割って各人ぶんに換算（`app/admin/payroll/page.tsx`）
- `staff_members.daily_wage` … 標準日当
- `lib/formState.ts` の `STAFF_DAILY_PAY` … ハードコードの日当（DBとコードに二重に存在）
- なぎささんは月給制（¥200,000）という注記が `staff_members.notes` にテキストで入っているだけ

→ **給与は「日当の記録」はあるが、実際にいつ・いくら支払ったかの記録はない。**

## 4. 「現金残高」はどこに入っているか

現在 `/cash`（`app/cash/page.tsx`）が計算している式：

```
手元現金 = cash_settings.opening_balance
         + Σ daily_reports.sales_amount        （start_date 以降）
         − Σ daily_reports.expenses[].amount   （同上）
         − Σ advance_expenses.amount（settled=true のぶんだけ）
```

- `cash_settings`：1行だけ持つ（期首残高＋起点日）
- `cash_ledger_settings` / `cash_ledger_entries`：**同じ目的の新しいテーブルが別に作られているが、データ0件で未使用**
- 銀行口座の残高は**どこにも入っていない**（キャッシュレス入金は、売上が全額現金のため対象外）

## 7. 調査中に見つかった注意点（そのまま報告事項）

1. **`advance_expenses` テーブルが既にある（0件・未使用）。**
   `/cash/advances` に管理者向けの画面もある。今回作る `keiri_advance_expenses` とは
   **別テーブル**（名前が違うので衝突しない）だが、**同じ「立替」を2か所に入れる形になる**。
   既存画面には「※ 日報の『立替経費』とは別物です（同じものを二重に登録しないでください）」という
   注意書きが既に出ており、**今回さらに3つ目の入口が増える。**→ 判断を仰ぎたい（本文レポート参照）。

2. **`cash_ledger_*` と `cash_settings` が二重に存在する**（どちらも現金残高用。前者は0件）。

3. **`daily_reports.expenses_total` はバグで使われていない**（集計は jsonb を都度合計）。

4. **`pkmn_*` テーブルは別事業**。経理層の集計対象に入れないこと。

5. **`interim_reports`（途中経過）を売上として足さないこと**。日報と二重計上になる。
